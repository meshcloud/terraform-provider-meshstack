# meshStack Provider

The meshStack terraform provider is an open-source tool, licensed under the Apache-2.0, and is actively maintained by meshcloud GmbH. The provider exposes APIs of meshStack to manage resources as code.

**Note:** This provider version requires meshStack version 2026.42.0 or higher. The provider automatically validates version compatibility during initialization.

## Authentication

~> **Preview:** The `profile` and `workspace` arguments may change without prior notice while the meshStack CLI is under active development.

### Available Authentication Methods

* **[meshStack CLI](https://github.com/meshcloud/meshstack-cli):** Use the current meshStack CLI profile or select an existing profile by setting the `profile` provider argument or `MESHSTACK_PROFILE`.
  * The provider refreshes stored browser logins automatically but never opens a browser.
  * Browser logins require a workspace identifier set via the `workspace` provider argument or `MESHSTACK_WORKSPACE`. The provider does not use the profile's default workspace saved during login, so a configuration acts in the same workspace for everyone who applies it.
  * That workspace only decides which of your workspace roles the provider acts with. A resource names its own workspace, such as `metadata.owned_by_workspace` of `meshstack_project`, so an Organization Admin still manages the resources of every workspace.
* **API key (recommended for automation):** Set `MESHSTACK_API_KEY` (the key's client ID) and `MESHSTACK_API_SECRET`.
* **Existing access token:** Set `MESHSTACK_API_TOKEN` (for example, from a building block run). The provider does not renew tokens or change their workspace scope.

Setting `endpoint` or `MESHSTACK_ENDPOINT` is required, unless a CLI profile supplies it.

~> **Security Note:** Set secrets using environment variables (`MESHSTACK_*`) rather than setting sensitive arguments like `apisecret` or `apitoken` directly in the provider block.

### Precedence and Defaults

Provider arguments take precedence over their `MESHSTACK_*` environment variable counterparts, listed in the schema below.
A CLI profile supplies the endpoint default.
Its stored credentials are used only when no API key or access token is configured explicitly.
An incomplete API key configuration fails rather than using a profile's stored secret.

If neither `profile` nor `MESHSTACK_PROFILE` is set, profile selection follows this order:

1. A unique match for `endpoint` or `MESHSTACK_ENDPOINT`.
2. The current CLI profile.
3. The profile named `default`.

With no arguments or environment variables set, the current CLI profile (or `default`) must supply the endpoint and credentials. Run `meshstack login` to create one.

## Example Usage

```terraform
# A browser login, stored in a meshStack CLI profile by `meshstack login`. The profile carries
# the endpoint and the credential. The workspace picks the role this configuration acts with.
provider "meshstack" {
  profile   = "my-profile"
  workspace = "my-workspace-ab12c"
}
```

```terraform
# An API key, with its secret exported as MESHSTACK_API_SECRET rather than written here, so that it
# reaches neither the configuration nor terraform state.
provider "meshstack" {
  endpoint = "https://api.my.meshstack.io"
  apikey   = "API_KEY"
}
```

```terraform
# A browser login acts in one workspace per provider block, so manage several workspaces with an
# aliased block each
provider "meshstack" {
  alias     = "team_a"
  workspace = "team-a-ab12c"
}

provider "meshstack" {
  alias     = "team_b"
  workspace = "team-b-cd34e"
}

resource "meshstack_building_block" "team_a_sandbox" {
  provider = meshstack.team_a
  # ...
}
```

## Schema

### Optional

- `apikey` (String) The client id of a meshStack API key to authenticate with, together with its secret, also read from `MESHSTACK_API_KEY`.
  
  Setting this here with the secret in `MESHSTACK_API_SECRET` keeps the secret out of the configuration and out of state.
- `apisecret` (String, Sensitive) The client secret belonging to the API key, also read from `MESHSTACK_API_SECRET`.
  
  Always set this through the environment: a value set here is written to Terraform state.
- `apitoken` (String, Sensitive) A meshStack access token to send as it is, also read from `MESHSTACK_API_TOKEN`.
  
  The token is minted elsewhere, so nothing renews it and nothing asks for a workspace: it already carries the one it was minted for. A building block runner's token is the usual one to bring here, to see what a run sees, and such a token may not be allowed to list workspaces at all.
  
  Always set this through the environment: a value set here is written to Terraform state.
- `endpoint` (String) The meshStack API to act against, such as `https://api.example.meshcloud.io`, also read from `MESHSTACK_ENDPOINT` and inferred from current profile if possible.
- `profile` (String) The profile whose credentials and defaults this run uses, also read from `MESHSTACK_PROFILE`.
  
  A profile is a named bundle of endpoint and credential, written by `meshstack login` into the meshStack CLI's configuration directory. It supplies each of those only where nothing above it did, so it is never an override.
  
  With no name given, the profile is the one whose endpoint matches the endpoint in use, else the one the last `meshstack login` selected, else `default`.
- `workspace` (String) The workspace to act in, identified as in meshPanel, such as my-workspace-ab12c. Also read from MESHSTACK_WORKSPACE.
  
  A browser login needs this or `MESHSTACK_WORKSPACE`: the provider does not take the profile's default workspace, which `meshstack login` stores. An API key or an API token needs no workspace.

## Dependency Wiring Patterns

Many meshStack resources depend on other meshStack objects. Prefer reusable references from data sources and computed outputs:

- Prefer plural data sources with `one(...)` when your filter selects exactly one match.
- Use singular data sources mainly for existence checks where `metadata.uuid` is enough.
- Reuse computed outputs such as `ref`, `identifier`, `version_latest`, and `version_latest_release` to avoid hardcoded identifiers.

Example dependency graphs:

```text
BBD -> BB
meshstack_building_block_definition
  └─ version_latest / version_latest_release
     └─ meshstack_building_block.spec.building_block_definition_version_ref

Tenant BB dependency chain
meshstack_workspace
  └─ meshstack_location
     └─ meshstack_platform (identifier)
        └─ meshstack_landingzone
           └─ meshstack_tenant
              └─ meshstack_building_block (target_ref)
```
